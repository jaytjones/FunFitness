# FunFitness 3.1 "On Your Wrist, On the Map" — Design Decisions (draft, 2026-10-10)

Pre-3.1 plan items 4 and 5, plus the data questions the Watch and Live Activity raise. Each section
ends with a **recommendation** and what's **still open** for Jay. Nothing here is built yet.

Starting point (2.4): one app target, a widget extension (`FunFitnessWidgetsExtension`), SwiftData +
CloudKit private database (Production schema deployed), HealthKit distance import and write-back,
`ActivityWriter` as the single logging path, `celebrate()` capping celebrations per type.

---

## 1. Where GPS routes live

A tracked run produces thousands of `CLLocation` points. A CloudKit record is limited to about 1 MB,
and the Production schema now only accepts additions.

| Option | How | Pros | Cons |
|---|---|---|---|
| **A. HealthKit is the source of truth** | Record with `HKWorkoutBuilder` / `HKWorkoutRouteBuilder`; the route is saved with the `HKWorkout` | Shows in Apple Fitness/Health; syncs via the user's Health data; the Watch does this anyway with `HKLiveWorkoutBuilder`; no CloudKit size issue | Needs HealthKit permission including workout routes; users who decline Health get no stored route |
| **B. CloudKit only** | Compressed polyline in a SwiftData `Data` property with `@Attribute(.externalStorage)` (stored as a CKAsset) | Independent of HealthKit; one sync path | Duplicates what Health already stores; app-only |
| **C. Both** | Raw route in HealthKit (A), plus a downsampled polyline (~500 points) in SwiftData for map and Journey rendering | Fast drawing and sync independent of Health queries; full detail stays in Health | Two copies to keep consistent |

**Recommendation: C.** Treat HealthKit as the source of truth for the raw route, and keep a small,
externally stored display polyline in SwiftData. Model, CloudKit-legal (defaults, no relationship):

```swift
@Model final class RouteSummary {
    var activityID: UUID = UUID()          // links to ActivityLog.id (no relationship, CloudKit-legal)
    @Attribute(.externalStorage) var polyline: Data? = nil   // encoded, downsampled coordinates
    var distanceKm: Double = 0
    var startedAt: Date = Date()
    var healthKitWorkoutUUID: UUID? = nil
}
```

`ActivityLog` already has a stable `id: UUID` and `healthKitUUID`, so no change to it is required.
Add the model, run `-initCloudKitSchema` on a device, and deploy — additive, so it's allowed.

**Still open:** whether a user who declines HealthKit can still track GPS runs (B-style fallback),
and the downsampling target.

## 2. Recording on iPhone

- Location: `CLLocationUpdate.liveUpdates()` with a `CLBackgroundActivitySession` for background
  delivery; `UIBackgroundModes` gains `location`; `CLActivityType.fitness`. Needs
  `NSLocationWhenInUseUsageDescription`.
- HealthKit's docs now include "Building a workout app for iPhone and iPad" (`HKWorkoutSession` on
  iPhone). **Check its minimum iOS version** against our iOS 18 deployment target before relying on
  it; otherwise build the workout with `HKWorkoutBuilder` + `HKWorkoutRouteBuilder` after the run.
- The finished workout flows through `ActivityWriter` (tagging `healthKitUUID`), so the existing
  import de-dup by UUID keeps it from being counted twice.

**Decided (2026-10-16, built in 3.1 B1a):** keep the iOS 18 target. Track with Core Location
(`CLLocationUpdate.liveUpdates(.fitness)` + `CLBackgroundActivitySession`) and, when Health saving
is on, build the workout + route after the run with `HKWorkoutBuilder` + `HKWorkoutRouteBuilder`.
Tracking works without Apple Health; the route then lives only in `RouteSummary` (§1's open
question, answered: yes). Tracked entries use `ActivitySource.tracked`, and the HealthKit import's
fuzzy de-dup now covers them, so a Watch recording of the same run isn't counted twice.

**Future enhancement — bump to iOS 26:** iPhone `HKWorkoutSession` + `HKLiveWorkoutBuilder`
(WWDC25, "Track workouts with HealthKit on iPhone and iPad") would give live Health metrics
(active energy, heart rate from paired sensors), Lock Screen access to workout data, and Siri
start/pause control, at the cost of dropping iOS 18–25 users. Revisit when the user base allows.

## 3. Apple Watch

- **Tracked workouts** on the Watch use `HKWorkoutSession` + `HKLiveWorkoutBuilder`. They land in
  HealthKit, and the phone's **existing HealthKit import** picks them up — with the 2.4 change, those
  imports now celebrate. No custom sync needed for distance.
- **Quick-log of lifts, reps, and duration** has no HealthKit equivalent. Options: WatchConnectivity
  `transferUserInfo` to the phone, which calls `ActivityWriter`; or the Watch writing to the same
  SwiftData CloudKit store (slower to appear on the phone).
- **Recommendation:** WatchConnectivity for quick-log (reliable, queued, immediate when the phone
  is reachable); HealthKit for tracked workouts.
- Complication: WidgetKit accessory families on watchOS, reading a small snapshot the phone sends.

## 4. Journey Mode data

The development plan says Journey Mode "reuses existing milestone copy" for Austin → San Antonio →
Houston. That no longer works: milestone copy now differs per pack, and the Austin→Houston line was
removed as inaccurate (2.3.2).

**Recommendation:** journeys are **bundled, pack-independent data**, not CloudKit records:

```swift
struct Journey { let id: String; let name: String; let checkpoints: [Checkpoint] }
struct Checkpoint { let name: String; let cumulativeKm: Double; let latitude: Double; let longitude: Double; let fact: String }
```

- Progress is derived from total distance by a pure, date-explicit `JourneyEngine`, like the other
  engines. Only the user's chosen journey is stored: one additive `UserProfile.activeJourneyID: String`
  with a default.
- Checkpoint distances and facts go through the same sourced fact-check as the 2.3 copy before
  shipping.
- Crossing a checkpoint can reuse `celebrate()`'s one-per-event cap, or show a lighter in-line toast.

**Still open (Jay):** which journey ships first. Candidates:
- **Texas Triangle** (Austin → San Antonio → Houston → Dallas → Austin, roughly 700 mi by road) — the
  plan's original idea, short enough to finish.
- **Appalachian Trail** (Georgia → Maine, 2,197 mi, well-documented shelters and towns) — matches the
  D10 "Appalachian Trail Complete!" badge.

## 5. Live Activity

- Lives in the existing `FunFitnessWidgetsExtension`. Add an `ActivityAttributes` type in a file
  compiled into both the app and the extension, plus `NSSupportsLiveActivities = YES` in the app.
- Content: elapsed time, distance, and the current reference-unit phrase ("2.3 km is 1 honeybee
  flight to the flowers").
- Updates come from the app while it records in the background; no push tokens needed for v1.

## 7. Testing implications

GPS and Watch need physical field testing (the plan already calls this out). Keep every new engine
(`JourneyEngine`, route downsampling, pace math) pure so the bulk stays unit-tested on the simulator,
and keep device testing for capture, battery, and sync.
