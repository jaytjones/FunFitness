# FunFitness 3.4 "Bring Your Friends" — Design Decisions (2026-11-24)

Internal development notes for 3.4. The release plan is in `FunFitness_Sequenced_Development_Plan.md`
(Release 3.4); this doc records the decisions, the limitations (what users are told and what the
team needs to know), and how 3.4 is gated.

## Decisions (Jay, 2026-11-24)

| # | Question | Decision |
|---|---|---|
| — | Backend | **Apple-only:** Sign in with Apple for identity, CloudKit for shared data. No backend of our own until non-Apple devices are a real need. |
| — | Where shared data lives | **Shared zones** (Jay, 2026-11-24): each person's Friends data sits in a "Friends" zone in their own private iCloud database, shared with each friend through one zone-wide `CKShare` with no public access. iCloud enforces who can read it. |
| 1 | How friends find each other | **Both** an invite link and a short code. No search, no contacts matching. |
| 2 | Duel scoring | **Effort Points**, so walking, lifting and yoga compete fairly. |
| 3 | Default sharing | **Nothing shared until turned on.** A new profile shows only name, emoji avatar and style. |
| 4 | Who sees 3.4 | **Internal testers only** until Jay launches it. Gated by the `INTERNAL_SOCIAL` build flag (see Gating). |
| 5 | Where sign-in lives | A **Profile section** for now; add a Friends tab only if Profile gets cluttered. |
| — | User documentation | The limitations below **must be explained to users** in the app and store/privacy text. |

## Gating: internal testers only

- All 3.4 code is wrapped in `#if INTERNAL_SOCIAL`, in its own folder `FunFitness/Social/` where possible.
  The flag is set (project-level `SWIFT_ACTIVE_COMPILATION_CONDITIONS`) in **Debug** and **Internal** only,
  never **Release**. `BuildFlagsTests` fails if Release ever gets it; `BuildFlags.internalSocial` exposes it.
- Internal builds (FunFitness Internal scheme) go only to the internal TestFlight group. Release builds for
  everyone else contain no Friends code or strings (checked by searching the built Release binary).
- **No owner check**, unlike the styles: testing friends needs two or more accounts, so any internal tester
  can use it. Internal testers must be App Store Connect users on the team.
- Same rules as the styles: Friends text stays out of `Localizable.xcstrings` until launch (`Text(verbatim:)`
  inside flagged code); shared code works with the flag on and off; launching = removing the `#if`s.
- CloudKit: Friends record types are created in the **Development** environment first; deploying them to
  Production is harmless to Release users (unused types) and is needed before Internal TestFlight builds
  (which use Production) can test Friends.

## Limitations

### Told to users (in the app, App Store text and privacy policy)

| Limitation | Where users are told |
|---|---|
| Friends needs an Apple device signed in to iCloud, plus Sign in with Apple. People on Android or the web can't join yet. | Before sign-in; "How Friends works"; App Store description; invite link landing text |
| Friends only: no search, no public leaderboards; you add people by invite link or code. | "How Friends works"; empty Friends section |
| Duel totals come from each person's own app and aren't verified, so they're for fun between friends. | Duel screens (one line); "How Friends works" |
| What friends can see (name, avatar, style, and only the stats you turn on) and that it's stored in Apple's iCloud for this app. Your workouts themselves are never shared. | Sharing settings; "How Friends works"; privacy policy; App Privacy answers |
| Updates can take a moment and need a network connection. | "How Friends works" |
| If FunFitness later works on other devices, your account carries over, but older feed items and finished duels may not. | "How Friends works" (short note) |
| Deleting your Friends profile removes you from friends' lists; your workouts stay. | Delete confirmation; sharing settings |

Copy: one short "How Friends works" page in FunFitness's voice, linked from the Profile section, the sign-in
screen and duel screens, plus one-line notes where each limitation matters.

### For the team (technical)

- **No server-side logic.** Nothing validates duel totals, rate-limits invites or high fives, or computes
  results; every rule runs in each app (`InMemorySocialService` documents them; the CloudKit version must
  apply the same ones). Two phones must reach the same duel result from the same records (`DuelEngine`).
- **Visibility is enforced by iCloud** (shared zones): only participants added to a person's zone-wide
  share can read their Friends zone; there is no public access. Invite *codes* still need a small lookup
  record that a stranger could find (step 3): it must hold only the code, an expiry and the share URL, which
  is useless to anyone who isn't added as a participant. Writing is limited to each zone's owner, so things
  sent *to* a friend (high fives, duel challenges) live in the sender's own zone and the friend reads them.
- **Storage counts against each person's own iCloud quota** (private database); tiny records, but a full
  iCloud account can't publish ("Your iCloud storage is full").
- **Identity:** people are keyed by `PersonID` = SHA-256 of the Sign in with Apple user ID (stable per
  developer team, carried over by Firebase/Supabase/our own backend). Never the iCloud user record ID.
  Without a server we can't verify Apple's identity token; within CloudKit the iCloud account is the real
  authentication. A future backend verifies tokens properly.
- **Sign in with Apple lifecycle:** check credential state at launch and handle revocation ("Stop Using Apple
  ID" in Settings): sign out locally and treat it like deleting the social profile. Apple only shares the
  name/email on the first sign-in; we don't use either (people choose a display name).
- **iCloud required:** Friends data lives in the person's iCloud, so it needs an iCloud account. Signed-out or restricted
  iCloud → Friends explains why and stays off; the rest of the app is unaffected.
- **Propagation:** CloudKit subscriptions drive pushes; delivery isn't guaranteed or instant, so screens
  refresh on open/pull. Shared zones suit invite-only friends, not public scale.
- **App Review:** Sign in with Apple alone is fine (no other third-party logins). Account deletion must be
  available in-app (delete profile). Friends is user-generated content between invited people only; blocking
  is required and built in.
- **Moving to a backend later:** replace `CloudKitSocialService` with a backend `SocialService`; accounts carry
  over; migrate friendships (the only data that needs it); apps republish totals and unlocks. Personal workout
  sync leaving iCloud is a separate, larger job needed for non-Apple devices regardless.

## Storage decision: shared zones (Jay, 2026-11-24)

The public database was the first plan; Jay chose **shared zones** for stricter privacy. Zone `Friends` in the
private database (SwiftData's own sync zone is untouched) holds the person's `SocialProfile` record (step 2) and,
later, feed events, high fives they sent, and their duel records. One zone-wide `CKShare` (`publicPermission =
.none`, title "FunFitness Friends") is created with the zone; step 3 adds each accepted friend as a participant.
Deleting the zone deletes the share, so friends lose access at once.

## Built in step 3 (2026-11-24): invites, friends, remove, block

- **Handshake** (shared zones need each side to add the other): Ana's invite = public `FriendInvite`
  (`invite-<CODE>`: code, createdAt, expiresAt, her CloudKit user record name, her share URL) + a local
  `OutgoingInvite`. Bob's accept = adds Ana to his share + public `InviteResponse` (`response-<CODE>`: his user
  record name and share URL; a second use of the code fails on save) + a local `PendingAcceptance`. Ana's next
  sync adds Bob to her share, accepts his, deletes the invite; Bob's next sync accepts Ana's and deletes the
  response. Expired invites are withdrawn; unanswered accepts are dropped after 7 days.
- **Second private zone `FriendsLocal`** (not shared) holds `OutgoingInvite`, `PendingAcceptance`, `BlockedPerson`,
  so friends can't see your invites or block list. Everything is fetched by record ID or a full zone read:
  **no CloudKit indexes are needed**.
- **Public records hold** only a code, dates, an opaque app-scoped CloudKit user record name and a share URL
  that only added participants can open. Default public security roles apply (World read, Authenticated
  create, Creator write), so each person deletes only their own invite/response.
- Friends = Friends zones shared with me (shared database) minus blocked people. Remove = take them off my share
  and leave theirs. Block = remove + `BlockedPerson`, so invites between you are refused. Deleting the profile
  also withdraws open invites and leaves every friend's share.
- `SocialService.acceptInvite` now returns `.friends(profile)` or `.waitingForInviter`; new `openInvites()` and
  `syncInvites()` (run on every Friends refresh, at launch and when Profile appears).
- UI (Profile › Friends): friends list (⋯ menu: Remove, Block with confirmation), **Invite a Friend** → sheet with
  the code (read-aloud friendly) and a share link, "Waiting on N invites", code field + Add with a result line.
- **Invite links:** `funfitness://friend/<CODE>`, opened via `.onOpenURL` (switches to Profile; a code opened
  before sign-in waits until the profile exists). The URL scheme is registered in `Info.plist`, which every
  configuration shares, so Release builds register the scheme too; it does nothing there (no handler is
  compiled). A web landing page for people without the app is a later option.
- Tests: 6 more in `SocialSessionTests` / `SocialTests` (33 Friends tests in total).
- **Not yet verified on devices** (needs two Apple IDs): the handshake, share participant lookup by user record
  name, accept, remove, block.

## CloudKit schema (after step 3)

Record types created automatically in **Development** the first time each is saved from a Debug run:

| Database | Zone | Record types |
|---|---|---|
| Private | `Friends` (shared with friends) | `SocialProfile` (+ the zone-wide `cloudkit.share`) |
| Private | `FriendsLocal` (not shared) | `OutgoingInvite`, `PendingAcceptance`, `BlockedPerson` |
| Public | default | `FriendInvite`, `InviteResponse` |

One account is enough: a Debug run with the launch argument **`-initFriendsSchema`** saves a throwaway record of
each type (every field set) and deletes it, which creates all six in Development (console: "Friends schema
initialized"). Then deploy to Production (CloudKit Console › Deploy Schema Changes) once all six exist in Development, before an
Internal TestFlight build tests Friends. Production schema changes are additive only (no renames/removals).
